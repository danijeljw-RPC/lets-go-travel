# Slice 7 Outcome — Retention, Privacy Operations and Production-Readiness Certification

## Outcome

Slice 7 is implemented on branch `codex/slice-7-retention-production-readiness` for review into `dev`. It delivers a new `ReadyToGoTravel.Retention` feature module (explicit record-class/policy/trigger/expiry model, legal hold with matter scoping and an append-only audit trail, centralised deletion receipts), legal-hold-aware retention sweeps owned by each existing module against its own schema (Booking: webhook payload bodies, notification content, abandoned checkout state; Support: attachments, general and booking-related tickets, security audit records; Consumer: account-closure profile minimisation), a `legal-hold-officer` Keycloak role and staff-only legal-hold administration API, customer-initiated account closure, and a code-verifiable production-readiness catalog. Implementation completion does not activate retention sweeps or the legal-hold API in any checked-in configuration, and it does not supply LiteAPI, carrier, webhook, PCI, object-storage or legal-approval evidence for any still-open production gate.

The implementation follows the [Slice 7 design](../superpowers/specs/2026-08-10-slice-7-retention-privacy-production-readiness-design.md), [implementation plan](../superpowers/plans/2026-08-10-slice-7-retention-privacy-production-readiness.md), [Data Retention and Legal Hold](../security/data-retention-and-legal-hold.md), closed [OI-0011](../issues/closed/OI-0011-supplier-payload-retention.md) and [PLAN-0002](../plans/active/PLAN-0002-mvp-delivery.md).

## Retention Architecture

A new `ReadyToGoTravel.Retention` module (own `retention` PostgreSQL schema, own `RetentionDbContext`) owns exactly the concepts that are genuinely cross-module: legal holds and their scopes, the retention policy catalog, centralised deletion receipts, and the production-readiness catalog. It has no `ProjectReference` to Booking, Support or Consumer — those modules reference Retention instead, mirroring the existing Support→Consumer "call the public contract, never the private tables" precedent from Slice 6. Each owning module implements its own sweep against its own schema, calling `ILegalHoldGuard` before every destructive action and `IRetentionReceiptRecorder` after every batch.

Every record class is modelled as an explicit, strongly-typed lifecycle: `RetentionRecordClass` (a closed enum of the twelve classes in the approved schedule), `RetentionPolicyDefinition` (period value, `Days`/`Years` unit, documented trigger description, policy version, `Delete`/`DeIdentify`/`PolicyOnlyNoLiveSweep` action), and `RetentionPolicyCatalog.CalculateExpiry`/`IsExpired` as the single, pure-function source of truth for expiry math — every sweep calls this rather than computing a manual cutoff, which is deliberate: an earlier manual `now.AddDays(-periodValue)` cutoff calculation silently treated a 2-year policy as 2 days for one record class before it was replaced with catalog calls everywhere (see Defects Found and Fixed below). Sweeps are stateless, live-recomputed and idempotent: retention candidacy is recomputed fresh every cycle from stable historical trigger timestamps (ticket closure, webhook completion, checkout last-activity, etc.) rather than a pre-populated work queue, so there is no new durable queue/lease table to keep consistent, and reapplying tombstones after a restore is automatic once the worker resumes running.

Candidate selection follows one consistent pattern in every sweep to work around a real EF Core SQLite-provider limitation found while implementing this (the provider used by every unit test cannot translate `ORDER BY`, `<=`/`>=`, or `.AddDays()` calls against a mapped `DateTimeOffset` column, though PostgreSQL can): a cheap, server-side, non-`DateTimeOffset` prefilter narrows the candidate set, then `RetentionPolicyCatalog.IsExpired`, ordering and `Take(RetentionSweepConstants.BatchSize)` all run client-side in C#. Each batch is checked against `ILegalHoldGuard.ExcludeHeldAsync` once up front, then every individual candidate is rechecked with `IsHeldAsync` immediately before its destructive action — closing the race window between batch selection and the specific delete/redact statement. Both checks write a `GuardCheckHeld` audit event (see Defects Found and Fixed below for how the batch-level check's audit gap was found and fixed). Every batch, successful or not, ends with a `RetentionDeletionReceipt` (record class, policy version, action, success/failure counts, completion time, non-sensitive failure summary — never deleted content) and every per-item failure additionally raises a deduplicated `RetentionOperationalCase` so repeated failures stay visible without paging on every retry of the same underlying cause.

## Classifications Implemented

| Record class | Sweep owner | Action | Status |
| --- | --- | --- | --- |
| Webhook payload bodies (90d from successful processing) | Booking | Delete (redact `RawBody`, keep event identity/hash/correlation/outcome) | Live sweep |
| Customer-notification rendered content (90d from final delivery attempt) | Booking | Delete (redact `PayloadJson`, keep recipient reference/template/status) | Live sweep |
| Search/abandoned checkout state (30d from last activity) | Booking | Delete (whole `CheckoutSession`, re-verified not-yet-progressed immediately before delete) | Live sweep |
| Support attachments (90d from ticket closure) | Support | Delete (storage object + row + usage-counter decrements, atomic) | Live sweep |
| General support tickets (2y from closure) | Support | Delete (full aggregate: messages, attachments, tokens, audit events, notifications) | Live sweep |
| Booking-related support tickets (7y from closure) | Support | Delete (same aggregate teardown) | Live sweep |
| Security/privileged-access audit records (2y from audit event) | Support | Delete | Live sweep |
| Customer account closure (90d from closure, by analogy to the closest documented "minimise after terminal event" rule — see Material Decisions and Interpretations) | Consumer | De-identify (reset non-essential preference fields; `Id`/`Subject`/`Status`/`ClosedAtUtc` preserved) | Live sweep |
| Canonical booking/price/payment/refund/version evidence (7y) | — | — | Policy-and-calculator only; no live supplier data exists yet to sweep |
| Successful raw supplier payloads (90d) | — | — | Policy-and-calculator only; no raw-payload evidence table exists (production supplier integration remains disabled) |
| Ambiguous/exceptional raw supplier payloads (12mo) | — | — | Policy-and-calculator only, same reason |
| Traveller sensitive-field minimisation (90d from final travel completion) | — | — | Policy-and-calculator only; no live traveller-document data exists yet |

The four `PolicyOnlyNoLiveSweep` classes are not silently missing — they are explicitly encoded in `RetentionPolicyCatalog` with their documented period and trigger so the schedule is complete and traceable, but deliberately have no sweep implementation because enforcing them today would mean inventing data that does not exist yet or bypassing an existing immutability control with no real record to protect. This is recorded as an explicit scope boundary in the design doc, not an oversight.

## Legal Hold Architecture

`LegalHold` (matter reference, reason, authorised owner, review-by date, release fields) cannot be constructed with zero scope entries — there is no supported "any hold exists, block everything" shortcut. Each `LegalHoldScope` names a record class plus exactly one subject key (customer, component booking or support ticket), enforced both in domain code and by a PostgreSQL `CHECK` constraint (`ck_legal_hold_scopes_exactly_one_subject`) as defence in depth; protecting multiple subjects means multiple scope rows on the same hold, keeping matching an unambiguous equality check per record class rather than mixed AND/OR semantics. `LegalHoldAuditEvent` (`HoldOpened`/`HoldReleased`/`GuardCheckHeld`) is append-only, enforced by both an EF `SaveChanges` guard and a PostgreSQL trigger, mirroring the existing `booking.reject_booking_version_mutation()` pattern — legal-hold history is exactly as tamper-evident as canonical booking version history. `Release` is idempotent (a no-op success on an already-released hold, never overwrites the original release record).

Administration is a new staff-only surface: `/api/v1/retention/legal-holds` (create, list, get, release) requires a new `legal-hold-officer` Keycloak realm role and authorization policy, implemented with the same custom `AuthorizationHandler`-parses-`realm_access` pattern as Slice 6's `support-agent` policy, and is never reachable by an ordinary customer token. This was the one point in this slice where the repository had no existing answer — no compliance/legal role or API existed anywhere before Slice 7 — and the user was asked directly; **"New staff-only role + API"** was the confirmed direction, implemented exactly as described.

## Legal-Hold Protection Correctness

Protection is deliberately not a blanket "any active hold exists" check: `LegalHoldScope.Matches` requires both the exact record class and the exact subject to match, verified directly in the clean-drill run below (a hold scoped only to `GeneralSupportTicket` correctly did **not** protect a `SecurityAuditRecord` linked to the same ticket, which the sweep correctly deleted in the same cycle). Race and lifecycle scenarios covered by automated tests and the live drill: not-yet-expired, expired-and-unheld, expired-and-held, an unrelated hold on a different subject, an unrelated hold on a different record class, multiple overlapping holds on the same subject, hold-created-then-released-before-expiry, hold released after expiry (record swept on the next cycle), a failed release (idempotent, safe to retry), and the batch-selection-to-deletion race window (closed by the mandatory `IsHeldAsync` per-item recheck immediately before every destructive action, independent of the batch-level `ExcludeHeldAsync` pre-filter).

## Privacy, De-identification and Account-Closure Behaviour

De-identification never deletes the stable identifiers needed to explain retained evidence: webhook/notification redaction empties only the raw body/payload column while event identity, hash, correlation, template, recipient reference and processing outcome survive; account-closure minimisation resets only `PreferredLocale`/`DisplayCurrency` to their defaults while `Id`, `Subject`, `Status` and `ClosedAtUtc` are preserved exactly, matching the retention baseline's "stable internal identifiers preserve evidence relationships without retaining unnecessary data."

`Customer.Close` is customer-initiated (`POST /api/v1/consumer/me/close`), idempotent, and immediately denies further customer-scoped access — `ConsumerBookingContextResolver` already filters booking-context resolution to `Status == Active`, so closure is a concrete, testable access-denial control the moment it is recorded; Keycloak owns credential/session termination separately, per [Identity and Access](../security/identity-and-access.md). Minimisation only proceeds after `IConsumerRetentionEvidencePort` (implemented once per module via dependency inversion — Booking and Support each register their own adapter, and Consumer aggregates `IEnumerable<IConsumerRetentionEvidencePort>` so every registered contributor must agree the customer has no protected evidence) confirms there is no still-retained booking, payment, refund, dispute or support-ticket evidence for that customer; both the "no protected evidence" and "linked to a still-open support ticket" paths are covered by automated tests and by the live drill below.

## Production-Readiness Catalog

`ReadinessCatalog` is a code-verifiable, fail-closed projection of the [Remaining Review Register](../decisions/review-register.md) — it is not a replacement for that register, and it can never mark a Blocking gate satisfied on implementation completeness alone: `ReadinessGate.Satisfied => !Blocking || Verification == ExternallyVerified`. It reports eleven gates as of this slice, mirrored in the new hand-authored [Production-Readiness Certification](../operations/production-readiness-certification.md): the five carried-forward LiteAPI/carrier/webhook/PCI/legal gates remain `Unverified`/`Blocking`; the Slice 6 object-storage/malware-scanning gate remains `Unverified`/`Blocking`; two new gates are added by this slice — **Retention sweep production activation** (`LocallyVerified`, `Blocking` — every concretely-scoped sweep is implemented, legal-hold-aware and verified against a live PostgreSQL drill, but `Retention:Enabled` defaults `false` in every checked-in configuration until production evidence is recorded) and **Legal-hold-officer role provisioning** (`Unverified`, non-Blocking — the role, policy and API are implemented and tested; named staffing is operational evidence, not a design question); and two operations-owned infrastructure gates (backup/restore evidence, diagnostic log retention) remain `NotStarted`, explicitly flagged as external evidence this repository's code cannot self-certify. `ReadinessCatalog.Ready` is currently `false`, correctly, because five Blocking gates remain below `ExternallyVerified` — this is a valid, honestly reported result: implementation is complete where scoped, launch remains blocked by outstanding external gates.

## Worker and Configuration Wiring

Retention sweeps run inside the existing general `ReadyToGoTravel.Worker` cooperative-worker cycle, chained alongside the Slice 5/6 webhook/notification/attachment-scan processors — no new deployable container was introduced. `RetentionSweepOptions.Enabled` defaults `false` in every checked-in `appsettings.json`/`appsettings.Development.json` across both the API and Worker hosts, matching the exact precedent set by `Support:Storage`/`Support:Scanning` in Slice 6. The Worker resolves `ConnectionStrings:Retention`, falling back to `ConnectionStrings:Booking` when unset, following the same fallback pattern already used for `Support`.

## Defects Found and Fixed

Adversarial self-review and live PostgreSQL drilling (not just successful compilation and green unit tests) found and fixed four real defects before this branch was pushed:

1. **Legal-hold guard audit gap.** `ILegalHoldGuard.ExcludeHeldAsync` — the batch pre-filter that protects the overwhelming majority of held items in practice — never wrote a `GuardCheckHeld` audit event; only the rare per-item `IsHeldAsync` recheck did. Found via a live PostgreSQL drill. Fixed by recording one audit event per suppressed candidate in `ExcludeHeldAsync` too, so "held records are... audited" (the documented baseline) is actually true for the common path, not just the rare one.
2. **Orphaned attachment references under partial failure.** `SupportRetentionSweepProcessor.DeleteTicketAggregateAsync` deleted every attachment's storage object up front, then deleted the attachment rows inside the same transaction as the rest of the ticket teardown — a later failure anywhere else in that transaction rolled the row deletions back while the storage objects stayed permanently deleted, resurrecting rows that pointed at nothing. Found during manual adversarial review of failure-window behaviour. Fixed by pairing each attachment's storage delete with its own row delete atomically, before the ticket-teardown transaction even opens; the remaining pure-Postgres-state teardown is safe to batch in one transaction because a rollback there has no external side effect to strand.
3. **Attachment-purge quota-counter drift under partial failure.** The standalone 90-day attachment sweep (for tickets closed but not yet at their own retention expiry) deleted an attachment's storage object and row, then separately decremented `TicketAttachmentUsage.BytesUsed`/`MessageAttachmentUsage.FileCount` as two more independent statements; a crash between the row delete and either counter update left that ticket's upload quota permanently overstated, with no retry possible since the deleted row can never be selected again. Reachable in practice because `SupportTicket` can reopen (a new message clears `ClosedAt`), re-enabling uploads against the now-wrong counters. Found during the same adversarial review pass. Fixed by wrapping the row delete and both counter decrements in one transaction, with the (independently idempotent) storage delete staying outside/before it.
4. **Retention could not actually delete tickets in production.** The most serious defect, found only by the live PostgreSQL upgrade-and-drill run below: Slice 6's `reject_support_ticket_message_mutation` trigger blocked both `UPDATE` and `DELETE` on `support_ticket_messages`, but Slice 7's approved schedule requires deleting an entire ticket's message history at its 2-year/7-year expiry. `DeleteTicketAggregateAsync`'s bulk delete was rejected by this trigger on every single cycle, permanently blocking every general/booking-related ticket deletion in production — invisible to all 183 SQLite-backed Support tests because migration-only raw trigger SQL is never executed against SQLite's `EnsureCreatedAsync` model. Fixed with migration `20260810110000_Slice7SupportTicketMessageRetentionDelete`, relaxing the trigger to reject `UPDATE` only; a full-repository search confirmed the retention sweep is the only code path that ever deletes ticket messages, so this closes exactly the gap without reopening any other route to silently removing message history. A new offline regression test (`TicketMessageAppendOnlyTriggerRejectsUpdateButAllowsRetentionDelete`, using `IMigrator.GenerateScript()` — no live database needed) now asserts the final trigger definition, so a future regression fails immediately in the normal test run rather than requiring another live drill to notice.

During the same review pass, three unused domain methods (`WebhookInboxItem.RedactRawBody`, `NotificationOutboxItem.RedactPayload`, `Customer.MinimiseProfile`) were found and removed: each sweep actually performs its redaction via `ExecuteUpdateAsync` directly (needed for batch SQL efficiency and the self-limiting WHERE-clause idempotency idiom used throughout this slice), so the methods were dead code from the start rather than a regression.

## Material Decisions and Interpretations

- **Legal-hold administration and authorization** (no existing repository answer): the user was asked directly and chose a new staff-only Keycloak role plus a staff-only API mirroring the Slice 6 support-console pattern, implemented exactly as confirmed.
- **Account-closure minimisation grace period**: [Data Retention and Legal Hold](../security/data-retention-and-legal-hold.md) documents that account closure "schedules eligible customer/profile data for deletion" but does not state a specific numeric grace period for that minimisation. 90 days was used by analogy to the closest documented "minimise personal fields after a terminal event" rule (traveller sensitive-field minimisation, 90 days after final travel completion) rather than an invented figure, and is recorded in code with that reasoning. This was judged low-stakes enough not to warrant interrupting implementation for a second question — the only fields minimised are non-sensitive display preferences (locale, currency), not traveller-identity or financial data — but is reported here explicitly rather than left implicit, since the original instruction named "account-closure semantics" as an example of a decision to surface.
- **Webhook-payload-body trigger**: the retention baseline's documented trigger is "Receipt"; the implementation uses `Status == Completed` and `CompletedAt` (successful processing) instead, because webhooks can be received and retried multiple times before succeeding once, and "receipt" has no single stable timestamp on a retry-with-backoff inbox. This is recorded explicitly in the design doc, not silently substituted, and only ever retains the body slightly longer than a literal receipt-time reading would.
- **An unrelated commit** (`6b46e87`, "add RTGT launch pages and Cloudflare deployment setup") landed on this branch from a separate concurrent session between two Slice 7 commits. Per the user's explicit direction, it was left in place rather than rewritten out of this branch's history; it is unrelated to Slice 7's retention/legal-hold/readiness scope.

### Live PostgreSQL Drill

A fresh PostgreSQL 17 container was started and all four `DbContext`s' migrations were applied in chronological order (`ConsumerDbContext` → `BookingDbContext` → `SupportDbContext` → `RetentionDbContext`) to reproduce a real upgrade from an empty database, confirming all five schemas and every `retention` table exist. Direct SQL against the live database confirmed: the `legal_hold_scopes` `CHECK` constraint rejects both a zero-subject and a two-subject row; the `legal_hold_audit_events` and `retention_deletion_receipts` append-only triggers reject a direct `UPDATE` and `DELETE` on both tables, with both rows confirmed unchanged afterward.

Realistic data was then seeded directly (an unprotected expired general ticket with messages; a ticket closed 100 days ago with an attachment, inside the ticket's own 2-year window but past the attachment's 90-day window; an expired ticket that would be placed under legal hold; a security audit record linked to that same ticket; an expired webhook payload body; an abandoned checkout past 30 days; a closed customer with no protected evidence; a closed customer with a still-open support ticket for the same subject) and a real legal hold was opened through `LegalHoldService.OpenAsync` (not raw SQL) scoped to the one ticket. Running the actual `ReadyToGoTravel.Worker` binary with `Retention:Enabled=true` against this database is what surfaced defect 4 above; after the trigger-relaxation migration was applied, a clean re-run confirmed every expected outcome: the unprotected ticket and its messages were fully deleted; the held ticket survived while its own security audit record — protected by a *different*, unscoped record class on the same hold — was correctly still deleted, directly demonstrating that legal-hold protection is per-record-class, not a blanket suspension; the webhook body was redacted with its status/identity intact; the abandoned checkout was deleted; the unprotected customer was minimised (`en-GB`/`GBP` → `en-AU`/`AUD`) while the customer still linked to an open support ticket was correctly left untouched; and every outcome was backed by a `RetentionDeletionReceipt` and, for the held items, `GuardCheckHeld` audit events. The attachment purge correctly and repeatedly failed closed (recording an operational failure, leaving the row and both usage counters exactly unchanged across every retry) because this drill environment runs with object storage disabled, matching the actual current production posture recorded in the readiness catalog — this is the documented fail-closed behaviour working as intended, not a defect. Releasing the hold through `LegalHoldService.ReleaseAsync` and running one more cycle then correctly deleted the previously-protected ticket, with a `HoldReleased` audit event recorded first.

## Production Gates and Exclusions

OI-0002, OI-0003, OI-0005, OI-0006 and the object-storage/malware-scanning gate remain unchanged and open; Slice 7 does not supply their evidence. This slice adds two new rows to the [review register](../decisions/review-register.md) and the new [Production-Readiness Certification](../operations/production-readiness-certification.md): retention-sweep production activation (implementation complete and locally verified against a live PostgreSQL drill; `Retention:Enabled` defaults `false` everywhere checked in) and legal-hold-officer role provisioning (implementation complete; named staffing is outstanding operational evidence, not a design question). Backup/restore evidence and diagnostic log retention remain explicitly flagged as external, operations-owned evidence this repository's code cannot self-certify — Slice 7's live-recomputation sweep design makes retention-tombstone reapplication after a restore automatic once a restored environment's worker resumes, but this has not been exercised against a real restored environment.

Slice 7 does not implement live sweeps for canonical booking evidence, raw supplier payloads (successful or exceptional) or traveller sensitive-field minimisation — see Classifications Implemented above — nor backup/restore execution itself (an infrastructure control, not application code), nor any capability beyond PLAN-0002's Slice 7 scope.
