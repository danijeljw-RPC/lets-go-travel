# Slice 6 Outcome — Support Tickets, Guest Magic Links and Private Attachments

## Outcome

Slice 6 is implemented on branch `codex/slice-6-support-magic-links` for review into `dev`. It delivers first-party support tickets with an immutable correspondence thread, authenticated customer access, anonymous guest ticket creation and access through a high-entropy magic-link bearer token, private S3-compatible attachments with fail-closed malware scanning, and a Keycloak-role-gated staff console. Implementation completion does not activate a production object-storage or malware-scanning backend, and no email vendor is selected.

The implementation follows the [Slice 6 design](../superpowers/specs/2026-08-09-slice-6-support-tickets-magic-links-design.md), [implementation plan](../superpowers/plans/2026-08-09-slice-6-support-tickets-magic-links.md), closed [OI-0012](../issues/closed/OI-0012-customer-support-model.md), [ADR-0010](../adr/accepted/ADR-0010-mvp-runtime-storage-and-delivery-baseline.md) and [PLAN-0002](../plans/active/PLAN-0002-mvp-delivery.md).

## Support Ticket Behaviour

A new `ReadyToGoTravel.Support` feature module (own `support` PostgreSQL schema, own `SupportDbContext`) implements the OI-0012 state model exactly: every ticket starts `New`; an accepted customer or guest reply moves it to `WaitingOnSupport`; an accepted support reply moves it to `WaitingOnCustomer`; an authorised support user closes it to `Closed`; an accepted customer or guest reply against a closed ticket reopens it to `WaitingOnSupport` while the closure remains a permanent entry in the immutable thread. A support reply against a closed ticket is rejected; only the customer or guest can reopen it. `SupportTicket.CustomerSubject` is the Keycloak subject for an authenticated ticket or `null` for a guest ticket; an authenticated customer's contact email always comes from the validated `sub`/`email` claims and cannot be overridden by the request body.

`POST /api/v1/support/tickets` accepts an optional consumer JWT so the same endpoint serves both authenticated and anonymous creation. Authenticated routes (`GET/POST /api/v1/support/tickets...`) resolve ownership from `sub`; another customer's ticket is `404 ticket_not_found`, matching the existing Consumer/Booking convention rather than a `403` that would confirm existence.

## Guest Magic-Link Security Model

A guest-created ticket receives a `SupportGuestAccessToken`: 32 bytes from `RandomNumberGenerator`, transported as an unpadded Base64Url string, with only its SHA-256 hash persisted (unique index on `token_hash`). The raw token exists only in memory during issuance and inside the single acknowledgement notification that carries it; it is never returned by any API response after issuance, never logged, and a "resend" action rotates to a new token rather than re-exposing the original. A token is valid for 30 days from issuance and is multi-use — it authenticates every request until it expires, is revoked, or is superseded by rotation, matching OI-0012's "can be revoked or rotated" framing rather than a one-time password-reset token.

Every guest route (`/api/v1/support/guest/ticket...`) carries no `ticketId` route or query parameter; the token is the only input that can select a ticket, resolved by hashing the supplied value and looking up the stored hash. A missing, malformed, expired or revoked token produces the same `401 guest_link_invalid` without distinguishing the reason, and every resolution attempt — success or failure — writes a `SupportAuditEvent` row, an internal table never exposed to the customer or guest. Rotation and revocation are staff-only (`POST /api/v1/support/staff/tickets/{ticketId}/guest-link/rotate|revoke`) and immediately invalidate the prior token; neither endpoint returns the raw token in its HTTP response.

## Attachment Security and Storage Model

`SupportAttachment` rows are private objects in an S3-compatible store via `AWSSDK.S3` (MinIO locally with `ForcePathStyle`, Amazon S3 `ap-southeast-2` in production once activated). The storage key is always server-generated as `support/{ticketId}/{attachmentId}{extension}`, with the extension coming from a fixed content-type-to-extension map — never from the client-supplied filename — eliminating path traversal and filename-injection risk from the object key entirely. The original filename is retained only as sanitised display metadata for the download `Content-Disposition`.

Uploads are validated against both the declared content type and the file's leading bytes (`%PDF-`, JPEG/PNG signatures, strict-UTF-8-without-NUL for text) before anything is persisted, enforcing the ADR-0010 limits: 10 MiB per file, 5 files per message, 50 MiB per ticket. A validated upload is stored immediately with `ScanStatus = Pending` and is not downloadable. A claim-lease worker cycle (`AttachmentScanProcessor`, following the exact `ExecuteUpdateAsync` claim pattern as the Slice 5 webhook inbox/notification outbox processors) retrieves the object and calls `IAttachmentScanner`; the production implementation (`ClamAvScanner`) speaks the ClamAV `INSTREAM` TCP protocol directly rather than adding a third-party scanning dependency. Only an explicit `Clean` result makes an attachment downloadable; `Infected` deletes the object and marks it permanently unavailable with an audit event; a scanner failure or unreachable scanner is treated as transient, retried with bounded exponential backoff, and never inferred as safe — after 8 exhausted attempts the attachment is marked `Failed`, never `Clean`. Production registers a disabled scanner (`DisabledAttachmentScanner`) and a disabled object-storage backend (`DisabledObjectStorage`) by default; both fail closed with an explicit "unavailable" outcome rather than silently succeeding, so attachments remain quarantined until both capabilities are configured and evidenced. Downloads require the caller to already be authorized for the ticket (owner, matching guest token, or `support-agent`), and the service independently re-checks that the attachment belongs to the resolved ticket before ever calling storage — defense in depth against IDOR even if an endpoint-level check were bypassed. A download returns a presigned URL valid for at most five minutes rather than a public object URL; attachments are never publicly addressable.

## Staff Console and Authorization

The privileged support console (`/staff/support`, `/api/v1/support/staff/...`) requires a new `support-agent` authorization policy backed by a custom `AuthorizationHandler` that parses the Keycloak `realm_access` claim's `roles` array, since ASP.NET Core does not flatten that nested claim automatically. The Web project keeps its own local copy of the same role-check logic (no `ProjectReference` to `ReadyToGoTravel.Support`, preserving the existing `WebProjectReferencesNoServerAssembly` boundary). The local Keycloak realm export gains a `support-agent` realm role. Per ADR-0010, impersonation is not implemented; every staff action records the acting subject in the thread or audit trail.

## Database and Configuration

The `support` schema adds seven tables: `support_tickets`, `support_ticket_messages` (append-only), `support_guest_access_tokens`, `support_attachments`, `attachment_scan_work`, `support_notification_outbox`, `support_audit_events`. Migration `20260809010000_InitialSupportSchema` installs a PostgreSQL trigger `support.reject_support_ticket_message_mutation()` that rejects direct `UPDATE`/`DELETE` against `support_ticket_messages`, mirroring the Slice 5 `booking.reject_booking_version_mutation()` pattern, in addition to the same guard enforced in `SupportDbContext.SaveChanges`. Checked-in Production configuration sets `Support:Storage:Enabled=false` and `Support:Scanning:ClamAv:Enabled=false`; Development configuration also defaults both to `false` so existing local workflows are unaffected, with the runbook documenting how to opt in once MinIO/ClamAV are running locally. `deploy/local/compose.yaml` gains `minio` and `clamav` services (both loopback-only, health-checked); the official ClamAV image is `amd64`-only and is pinned to `platform: linux/amd64` so it still runs (under emulation) on Apple Silicon hosts.

While verifying the local runbook end-to-end, a pre-existing defect was found and fixed: `ReadyToGoTravel.Worker` and `ReadyToGoTravel.FlightReconciliation.Worker` called `AddBookingModule` (which unconditionally registers `CheckoutService`/`BookingHistoryService`, both depending on `IConsumerBookingContext` from the Consumer module) without ever calling `AddConsumerModule`, so either host throws `InvalidOperationException` from DI validation on startup. This predates Slice 6 and is unrelated to Support; it was not previously caught because nothing had exercised `dotnet run` for either worker with a real service-provider build. Both `Program.cs` files now also call `AddConsumerModule` against the same connection string, and both `.csproj` files gained the corresponding `ProjectReference`.

## Codex Review Response

The automated Codex review of the initial pull request found two P1 and three P2 issues, all confirmed valid against the actual code and fixed:

- **P1 — raw guest token persisted in the durable notification outbox.** `SupportNotificationOutboxItem.PayloadJson` originally carried the raw magic-link token, and in Production (no registered sender) that row never reaches `Sent`, so the token sat in plaintext indefinitely — contradicting the "only the hash is stored" model. Fixed by deferring token minting from ticket-creation time to actual send time: the durable payload never contains a token; `SupportNotificationOutboxProcessor` mints a fresh one (`IGuestAccessTokenService.RotateAsync`) in memory immediately before each send attempt and never writes it back to the row.
- **P1 — a rotated guest token was never delivered.** `RotateGuestLinkAsync` revoked the previous token and discarded the new one. Staff rotation now sends the new link synchronously (immediate feedback, no durable plaintext token anywhere) and the response reports whether delivery succeeded, without ever including the token itself.
- **P2 — no staff attachment-download route.** Added `GET /api/v1/support/staff/tickets/{ticketId}/attachments/{attachmentId}/download`, the corresponding `SupportStaffApiClient` method, and a download control on the staff ticket page.
- **P2 — closing an already-closed ticket crashed on a duplicate outbox dedupe key.** `CloseAsync` now returns early (no re-enqueue) when the ticket is already `Closed`, matching the ticket domain's own no-op-on-repeat-close behaviour.
- **P2 — message bodies exceeding the persisted 4,000-character column limit were not rejected before insert.** All four entry points (ticket creation, and authenticated/guest/staff replies) now validate length and return `400 support_message_too_long` instead of letting PostgreSQL reject the insert.

Eight regression tests were added covering each fix (durable-payload-never-contains-token, token-minted-and-sent-exactly-once-at-send-time, staff-rotation-delivers-the-new-token, idempotent double-close, message-length rejection on all four entry points, staff attachment download). The full suite grew from 329 to 337 passing tests; `dotnet restore --locked-mode`, `dotnet format --verify-no-changes`, `dotnet build`, the full test suite, `dotnet ef migrations has-pending-model-changes`, `bash scripts/validate-docs.sh`, `git diff --check` and all four Docker builds were re-run after these fixes and all pass. The live end-to-end smoke test recorded below predates the P1 token-persistence fix (its walkthrough is what surfaced the token sitting in `support_notification_outbox.payload_json`); the fix itself is verified by the new automated regression tests above rather than a repeated live walkthrough, since the security property (no raw token in a durable column) is exactly what those tests assert against a real SQLite-backed `SupportDbContext`.

## Production Gates and Exclusions

OI-0002, OI-0003, OI-0005 and OI-0006 remain unchanged and open; Slice 6 does not supply their evidence. This slice adds one new production-readiness item to the [review register](../decisions/review-register.md): object storage and ClamAV malware scanning default to a disabled/unavailable posture, so support attachments remain quarantined in production until a provisioned Australian-region S3-compatible bucket, credentials, and a production ClamAV deployment are configured and evidenced. `ISupportNotificationSender` has no production implementation, matching the Slice 5 notification posture — no email vendor is selected or invented.

Slice 6 does not implement Slice 7 retention enforcement or legal-hold tooling (it stores the closure/creation timestamps that enforcement will need), live chat, staff impersonation, or any other PLAN-0002 deferred capability. The pull request must not be merged as part of this outcome.
